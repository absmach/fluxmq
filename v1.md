# FluxMQ v1.0 Stable-Core Hardening Plan

## Summary

FluxMQ has a credible v1 foundation, but it is not release-ready today. The codebase is substantial—about 96.6K production Go lines, 62.7K test lines, 1,625 tests, and 86 benchmarks—but the remaining risks sit at system boundaries: privileged APIs, crash durability, DLQ transitions, cluster security, distributed testing, and release publishing.

The selected v1 contract is:

- Production-supported: MQTT 3.1.1/5.0, AMQP 0.9.1/1.0 documented subsets, single-node durable queues, and secure broker clustering.
- Experimental and disabled by default: queue Raft, HTTP/CoAP bridges, and incomplete protocol extensions.
- Performance: reproducible reference profiles and regression budgets, not unverified 500K-connection or 100K-msg/s claims.
- Admin security: file-backed bearer tokens with viewer/operator/admin RBAC.

Estimated delivery budget: **approximately 54–81 engineer-days**, or approximately **13–18 calendar weeks for one engineer** and **8–11 weeks for two engineers**, including a final two-week soak. Confidence is medium, ±25%.

## Current Assessment

Validation performed:

- `go test -short -race -failfast -timeout 3m ./...`: passed in 106.8 seconds before the latest local performance edits.
- `golangci-lint run`: passed with zero issues at that snapshot.
- Current focused topic/index tests passed.
- `govulncheck ./...`: no called vulnerabilities; one required module contains unreachable vulnerable code.
- Full race integration package failed once after 349 seconds; the isolated leader-failover test then passed in 22 seconds. Package-level reliability and cleanup remain unproven.
- There are no fuzz targets.
- The worktree moved during the review and contained user-owned topic-index benchmarks and optimizations; those were treated as in-progress evidence rather than a release baseline.

Material findings:

| Priority | Finding |
| --- | --- |
| P0 | The admin HTTP and Connect queue services have no authentication middleware and expose reload, append, queue deletion, purge, truncate, session, and consumer operations. The default Compose stack publishes this API to the host. See `server/api/server.go:58` and `deployments/docker/compose.yaml:8`. |
| P0 | Ordinary durable-queue publishes use buffered `Append`, while only the protected internal stream uses `AppendAndSync`. Successful ordinary publishes can lose up to the background-sync window after a process or host crash. See `queue/manager.go:1099` and `logstorage/adapter.go:220`. |
| P0 | DLQ failure is lossy: max-delivery processing removes the PEL entry regardless of DLQ success, and explicit Reject never invokes DLQ. See `queue/consumer/manager.go:439`. |
| P0 | Queue replication fails open: a replication-enabled queue appends locally when Raft is unavailable, and `local` write policy bypasses consensus. `replication_factor` and `min_in_sync_replicas` are largely validated/logged rather than enforced. See `queue/manager.go:861`. |
| P0 | Broker gRPC has optional mTLS, but embedded-etcd peer/client traffic defaults to plaintext on all interfaces, and experimental Raft uses plaintext TCP. See `config/config.go:1094` and `queue/raft/manager.go:159`. |
| P0 | AMQP 1.0 holds connection slots through unbounded TLS, SASL, and AMQP handshakes. AMQP 0.9.1 already has the required deadline model. See `server/amqp1/server.go:120`. |
| P0 | CI runs only the short race suite, excluding integration, stress, interoperability, and cluster-failure scenarios. The release workflow pushes and tags images before scanning them and independently of CI success. See `.github/workflows/ci.yml:56` and `.github/workflows/build.yml:54`. |
| P0 | *Addressed.* Topic capture ran synchronously on the publish path of all three protocols, ahead of subscriber delivery, and the ordinary append honours no cancellation, so a stalled queue store delayed every subscriber of a matching topic and the publisher's acknowledgement. Capture now resolves its targets inline — an in-memory lookup — and dispatches the storage work to bounded per-queue lanes: enqueueing never blocks, a full backlog drops the newest job and counts it in `queues.capture_dropped`, per-queue append order is preserved, and shutdown drains within a timeout. A regression test hangs if capture is put back inline. Remaining: the backlog is bounded in jobs rather than bytes. See `queue/capture.go`. |
| P1 | The queue delivery address is ambiguous. `queueDeliveryTopic` preserves a captured message's source topic after the queue root, but absorbs the leading level when it already equals the queue name, so `$queue/m/acme/temp` means either a capture of `m/acme/temp` in queue `m` or an explicit publish to `$queue/m/acme/temp`, and a consumer cannot tell which. The source topic is therefore not recoverable from the address. This is a wire-visible delivery contract and is far cheaper to settle before v1 than after. See `queue/delivery_engine.go:664`. |
| P1 | Container health uses liveness rather than readiness. Readiness does not cover listener state, queue-log errors, cluster quorum, or required auth dependencies. See `server/health/server.go:165`. |
| P1 | Performance evidence is not release-grade: committed result artifacts are absent, queue delivery is globally serialized, matching remains O(relevant patterns), matching queue appends are serial, and legacy remote forwarding scans cluster consumers. |
| P1 | *Addressed.* Topic matching was linear in the number of patterns configured, scanning each under a shared read lock: 8 patterns 342 ns, 512 patterns 22 µs, 8192 patterns 193 µs, about a 5k publish/second ceiling on one core at the top end. Both halves of the index are now tries keyed on topic levels, so matching costs the topic's own depth instead. Measured flat: 37–72 ns unmatched and 172–325 ns matched, at every size from 8 to 8192 patterns. See `queue/storage/patterntrie.go`. |
| P2 | *Addressed with the above.* A publish addressed to a queue scanned every `$queue/` pattern linearly, roughly 1.5 µs at 32 queues and growing with queue count. The same trie indexes it: 248 ns, and flat at 8, 512 and 8192 queues. |
| P2 | `AsyncEventHook.Close` can race with enqueue and panic on a closed channel; HTTP auth/hook response bodies need consistent limits. These are small fixes but belong before API stability. |

The topic optimization has since landed with unit tests and committed benchmarks. `TopicMatch` no longer allocates, and the index partitions patterns by `$` prefix, so an ordinary publish on a broker whose queues are all `$queue/`-addressed consults no patterns at all: `PublishToMatchingQueues` for a non-matching topic measured roughly 27 ns and zero allocations at 32 queues and 33 ns at 512, against 4.2 µs/64 allocations and 67 µs/1024 allocations before.

Read that number for what it measures. Scaling `$queue/` patterns exercises the partition, which short-circuits them, so it flatters the matcher. The dimension that costs is the count of *ordinary* patterns, which is benchmarked separately. Both are now indexed by a trie rather than scanned, so neither grows with the number of patterns; one limit remains, that capture is asynchronous and bounded rather than free. All figures are from a review workstation and are not a release baseline; they should be revalidated on the reference profiles in Phase 4.

## Public Interfaces and Behavior

### Configuration v1

Every file starts with `version: 1`. Decoding is strict: unknown, duplicate,
legacy, and misplaced keys fail with their full YAML path. The YAML document
types are separate from normalized runtime configuration, defaults are applied
once during normalization, and reload compares normalized values. Listener,
storage, and cluster-topology changes remain restart-required.

Stable listeners are typed lists rather than a fixed plain/TLS/mTLS matrix:

```yaml
version: 1

listeners:
  mqtt:
    - address: ":1883"
      transport: tcp
      versions: ["3.1.1", "5.0"]
  amqp091: []
  amqp1: []

storage:
  type: badger
  data_dir: /var/lib/fluxmq
```

Listener limits and timeouts have deterministic defaults. An optional `tls`
mapping enables TLS; `client_ca_file` additionally enables mandatory client
certificate verification. AMQP 0.9.1 listeners select `auth: external|local`.
There are no `plain`, `tls`, `mtls`, `local`, `internal`, or `service` listener
slots or aliases. Admin, health, and telemetry are independent top-level
sections. HTTP and CoAP listeners exist only below explicit `experimental`
gates and do not appear in stable-core examples.

Starting without `--config` runs a loopback-only in-memory development broker
and emits an explicit warning. Naming a missing file is an error. Operators and
CI validate a file without starting the broker with:

```console
fluxmq config validate --config /etc/fluxmq/config.yaml
```

There is no general environment interpolation, include, overlay, or profile
engine. The only process-local override is cluster node identity.

### Admin API

Add `admin.auth` with:

- `mode: token|disabled`; disabled is allowed only on loopback.
- File-backed token entries with `viewer`, `operator`, or `admin` roles.
- Viewer: read-only stats, sessions, subscriptions, overview, and queue inspection.
- Operator: session disconnect and delivery operations such as append, ack, nack, and claim.
- Admin: queue lifecycle, purge, truncate, and configuration reload.
- `FLUXMQ_ADMIN_TOKEN_FILE` for dashboard-to-broker calls; never expose the token to browser JavaScript.

### Queue durability

- Add `storage.queue_ack_durability: fsync|buffered`, defaulting to `fsync`.
- Add `storage.queue_sync_interval` for explicitly buffered deployments.
- No storage-format change is required.

### Cluster security and experimental features

- Use one shared static manifest for every node:

  ```yaml
  cluster:
    members:
      node1: node1.internal
      node2: node2.internal
      node3: node3.internal
    ports:
      etcd_peer: 2380
      transport: 7948
    tls:
      ca_file: /run/secrets/cluster-ca
      cert_file: /run/secrets/cluster-cert
      key_file: /run/secrets/cluster-key
  ```

- The presence of `cluster.members` enables clustering; there is no `cluster.enabled`.
- Select the local member with `--node-id`, falling back to `FLUXMQ_NODE_ID`; the flag wins, and the selected ID must exist in `members`.
- Derive embedded-etcd membership, advertised peer URLs, transport peers, and per-node data directories from the member map, shared ports, node ID, and `storage.data_dir`. The embedded-etcd client listener stays on loopback as an implementation detail.
- Use the one cluster mTLS identity for embedded-etcd peer traffic and broker transport traffic. Non-TLS startup fails unless `cluster.allow_insecure: true` is set explicitly.
- Membership is static for v1. A changed member map against existing cluster data fails startup; elastic join and remove are post-v1.
- Transport batching and retained-payload thresholds are implementation details, not stable configuration.
- Put queue Raft below `experimental.queue_raft`, derive its membership from the same member map, and exclude it from the compatibility contract.
- Queue replication configuration without the experimental gate and a working Raft manager is a startup error.
- Unknown or unavailable write paths return errors rather than appending locally.

### Queue delivery addressing

A queue's topic patterns are matched against every publish, not only `$queue/`
addresses, so a pattern such as `m/#` captures ordinary pub/sub traffic on every
protocol. Captured messages are delivered under `$queue/<name>/`, with the
source topic preserved after the root.

The address must become unambiguous before it is frozen:

- Carry the source topic in an immutable broker-owned message property and treat
  the address as a queue identifier only. This is the preferred option: it
  survives any future addressing change and cannot be spoofed by a publisher.
- Alternatively, deliver as `$queue/<name>/<source topic>` unconditionally,
  rather than absorbing a leading level that happens to equal the queue name.
- Either way, state which one the v1 contract guarantees, and cover the
  queue-name/source-prefix collision in tests. Consumers currently cannot
  reconstruct the source topic, and today's advice — do not name a queue after
  the first level of its own pattern — is a workaround, not a contract.

### Protocol and health behavior

- Add AMQP 1.0 `handshake_timeout` to each listener, defaulting to 10 seconds. The deadline covers TCP/TLS, SASL, and AMQP Open and is cleared only after the connection is established.
- Extend readiness additively with listener, queue-log, cluster-quorum, and required dependency checks.
- Docker and Kubernetes examples use `/ready`; `/health` remains liveness-only.

## Release Acceptance

- All stable-core unit and integration suites pass under race detection on three consecutive clean runs.
- Previously unconditional stable-core skips—leader failover, subscription propagation, retained cross-node behavior, and takeover—are implemented or removed from the v1 support claim.
- Admin requests return 401 without credentials and 403 for insufficient roles; destructive operations produce structured audit events.
- Acknowledged fsync-mode queue messages survive SIGKILL and restart. Injected append/fsync/DLQ failures never remove the source PEL entry. Crash-window DLQ duplicates retain the same stable transfer ID.
- A secure three-node cluster passes formation, leader and follower loss, network partition, lease expiry, reconnect, session takeover, retained delivery, and graceful shutdown tests.
- Minimal files and omitted optional sections normalize deterministically; legacy keys, misspellings, duplicate keys, invalid listener/TLS combinations, missing named files, and unknown cluster node IDs fail with actionable paths.
- The same cluster YAML starts three nodes using only different node IDs; all shipped YAML and Compose examples pass the real strict loader/render checks in CI.
- MQTT 3.1.1 and 5.0 interoperate on one auto-detect listener; TLS/mTLS and AMQP external/local listener policies have end-to-end coverage.
- Clustering fails without mTLS unless the explicit insecure development flag is present, and changing a persisted static member map fails startup.
- MQTT is exercised with Mosquitto/Paho clients; AMQP 0.9.1 with `amqp091-go`; AMQP 1.0 with an independent client implementation.
- Parser fuzz targets cover MQTT 3/5, AMQP 0.9.1/1.0 frames and configuration decoding, with bounded PR smoke runs and longer scheduled runs.
- Reference workloads permit no unexplained throughput regression above 10%, p99-latency/RSS regression above 15%, or unexpected message loss.
- Release candidates complete a 72-hour secure three-node soak with repeated disconnects and node termination, followed by backup/restore and upgrade/rollback drills.
- No Critical/High called vulnerability remains; broker and dashboard images are scanned before publication and signed by immutable digest.

## Assumptions

- AMQP support means a clearly documented, interoperable subset—not full implementation of every AMQP operation.
- No FIPS certification, multi-user dashboard login system, or external identity provider is included; operators provision file-backed tokens.
- Existing storage data must upgrade without loss. Pre-v1 configuration is replaced outright: there are no aliases, compatibility decoding, or migration tools.
- v1 cluster membership is static and secure by default; runtime membership changes are deferred.
- Queue Raft, HTTP, and CoAP are experimental, disabled by default, and outside the stable configuration contract.
- The topic-index changes have landed with tests and committed benchmarks, but their figures come from a review workstation. They become the performance baseline only after being rerun on the Phase 4 reference profiles.
